# Contract

Cantfail asks whether a test can fail. Canaryfield asks whether the harness catches planted defects and suitediet asks which tests earn their runtime. Cantfail stays inside the first question only.

A test that stays green under a fixed panel of mutations is a candidate for review. A surviving mutant is evidence about that panel and about the analysed project only. It is never proof that a test can fail for no reason and it is never proof that a test can never fail at all.

## Setup obligations

Obligation S1 covers the seed. The repository carries the seed README and the MIT licence from its first commit and later work lands on branches rather than on the seed commit. This is covered by inspection of the repository history and by the status section of the README.

Obligation S2 covers the local gate. The repository test suite runs with python and pytest alone and needs no network access and no paid service. This is covered by tests in the tests folder and by the continuous integration workflow running the same command.

Obligation S3 covers honest status. The README status section records the remote seed state and the contract state without claiming work that has not landed. This is covered by inspection against this contract.

Obligation S4 covers synthetic fixtures. Every fixture and example in this repository is synthetic and carries no real trace and no private detail. This is covered by inspection of the examples folder and the tests folder.

## Slice 1 obligations

Obligation C1 covers static mock detection. The static scan flags a test that assigns a value to the return value of a mock and later asserts equality with that same value. The scan also flags an assertion that compares an expression with itself and an assertion on the constant true value. Each finding carries a file path and a line number. This is covered by tests in tests/test_static_scan.py.

Obligation C2 covers the fixed mutation panel. The panel applies return removal by returning no value and comparison inversion and numeric constant movement by one in both directions and boolean constant negation. The panel is fixed for slice 1 and every mutant records its kind and its source line. This is covered by tests in tests/test_mutations.py.

Obligation C3 covers safe execution. Mutants run one at a time in a scratch copy of the analysed project and the analysed files are never written. The analysed files are byte identical after a run. This is covered by tests in tests/test_runner.py.

Obligation C4 covers the baseline. A test file whose unmutated run already fails is reported as a baseline failure and is never reported as decorative. This is covered by tests in tests/test_runner.py.

Obligation C5 covers per test file verdicts. A test file that stays green under every applicable mutant is reported as a decorative candidate and the report names its test functions and lists every mutant that walked through. A test file that turns red under at least one mutant is reported as able to fail under this panel. This is covered by tests in tests/test_runner.py.

Obligation C6 covers the report shape. The analysis produces a human readable text report and a JSON report with the same findings. Both reports carry the static findings and the per file verdicts and the surviving mutants. This is covered by tests in tests/test_report.py and tests/test_cli.py.

Obligation C7 covers conservative wording. Reports describe decorative results as candidates and survivors as mutants that walked through the panel. Reports never claim that a surviving mutant proves a test is worthless and never claim that a killed mutant proves a test is strong. This is covered by tests in tests/test_report.py.

Obligation C8 covers discovery. The runner pairs a test file with the source module of the same stem when one exists and otherwise pairs it with every non test source module in the project. Each run of a single test file under a single mutant has a timeout. This is covered by tests in tests/test_runner.py.

## Slice 2 obligations

Obligation D1 covers per test function verdicts. Every top level test function in a test file is judged on its own. The runner runs the fixed panel against that function alone by selecting its node in the scratch copy and records one verdict for the function. The verdict is one of four values. A function that turns red under at least one mutant is reported as able to fail. A function that stays green under every applicable mutant is reported as a decorative candidate. A function whose unmutated run already fails is reported as a baseline failure. A function with no applicable mutant is reported as having no applicable mutants. A run that times out never counts toward a decorative verdict. Class based tests are named only when they are plain functions in slice 1 and per function verdicts in this slice cover top level test functions. This is covered by tests in tests/test_functions.py.

Obligation D2 covers the file level rollup. The file level verdict is derived from the function verdicts and never from a separate whole file mutant run. A file is a decorative candidate only when every judged function in it is a decorative candidate and at least one function was judged. A function counts as judged when its baseline passed and at least one mutant applied to it. A file with at least one judged function that can fail is reported as able to fail. A file where no function was judged and at least one function failed its baseline is reported as a baseline failure. A file where no function was judged and no function failed its baseline is reported as having no applicable mutants. This is covered by tests in tests/test_functions.py.

Obligation D3 covers the report format version. The JSON report carries a top level field named schema and its value is cantfail-report/2. The text report and the JSON report both carry the per function verdicts with the same facts. The file level entry keeps its surviving mutants as the mutants that no judged function turned red. This is covered by tests in tests/test_report.py and tests/test_cli.py.

Obligation D4 covers honest runtime. The fixed panel does not grow in this slice. One scratch copy is made per mutant and every judged function runs inside that copy before the copy is removed. The baseline for each function runs in one shared scratch copy per test file. This is covered by inspection of the runner and by the local gate staying fast enough to run in the demo.

Obligation D5 covers one new static pattern. The static scan also flags an assertion that compares a call result with the exact literal a mock was configured with inside a helper or a fixture defined in the same file. The helper form covers a test that binds a name to a call of the helper. The fixture form covers a test that takes the fixture name as a parameter. The binding only forms when the helper or fixture returns the very mock it configured and the configured value is unambiguous. An assertion against a different literal is not flagged and a helper that returns an unconfigured object is not flagged. This is covered by tests in tests/test_static_scan.py.

Obligation D6 covers the pattern that was considered and rejected. An assertion that a mock was called was considered as a new pattern and rejected for this slice. A call assertion next to a configured return value does not on its own prove the test cannot fail for a real reason because the call itself may be the behaviour under test. No finding kind is emitted for call assertions in this slice. This is recorded here so the rejection is part of the contract and not a silent gap.

## Round 1 review fixes

The Round 1 audit and red team found ways the slice 2 claims could mislead. The obligations below amend D1 and D2 and D5 where they conflict, and each one is covered by tests in tests/test_round1_fixes.py unless it says otherwise.

Obligation FIX-1 covers duplicate names. A test function name defined more than once at module level is judged once, under the single name pytest can run. The earlier definition never executes and is never reported as judged on its own.

Obligation FIX-2 covers rollup precedence. A file is never reported as a decorative candidate while any function in it failed its baseline. When no judged function can fail and at least one function failed its baseline the file is reported as a baseline failure, even when every judged function is a decorative candidate.

Obligation FIX-3 covers class based tests. A file that carries class based test methods is judged at whole file level by the slice 1 behaviour, with the per function verdicts for its top level functions reported alongside. Such a file is never silently skipped and never reported as having no applicable mutants merely because its tests are methods. The file level entry records that it was judged whole file.

Obligation FIX-4 covers timeouts as their own verdict. A function whose baseline run times out, and a judged function that turns red under no mutant and has at least one timed out mutant run, are reported as inconclusive. Inconclusive is a fifth verdict value added by this amendment. A timed out mutant is never listed among the surviving mutants in either report, because a timeout is unknown and not a walk through.

Obligation FIX-5 covers method aware helper and fixture matching. The D5 pattern matches the configured call itself, named by the mock and the attribute chain that was configured. An assertion on a different method of the same mock is not flagged. A helper that configures several methods on one mock flags each configured call. One call configured with two distinct literals inside one helper stays unflagged for that call alone, and the rest of the mock still counts.

Obligation FIX-6 covers binding scope. Helper and fixture bindings live inside the function that creates them. A binding formed in one test function never flags an assertion in another function, and assigning a bound name to anything else clears the binding from that point on.

Obligation FIX-7 covers the rejected pattern test. The D6 rejection is pinned by a test showing that call assertions emit no finding. Obligation D4 stays inspection only by its own wording and that is now stated as a deliberate mapping rather than an oversight. One further recorded fact is that verdicts are assigned by execution, so a function that calls another test function inherits its killing power, and the baseline flag on a file verdict means at least one function passed its baseline in the rollup path and the whole file baseline in the whole file path.

## Slice 3 obligations

Obligation E1 covers per method verdicts. Every test method that pytest can select inside a class is judged on its own, alongside the top level test functions of its file. The runner selects a method by the node pytest gives it under its file, shaped as the file and the class name and the method name joined by double colons, and the verdict entry in the functions list of the file verdict carries that class and method shape as its name. A method carries the same five verdict values as a function and follows the same rules. A method whose unmutated run already fails is reported as a baseline failure and is never judged. A method whose baseline run times out, and a judged method that turns red under no mutant and has at least one timed out mutant run, are reported as inconclusive. A timeout never counts toward a decorative verdict for a method, just as it never does for a function. This is covered by tests in tests/test_methods.py.

Obligation E2 covers which classes yield selectable methods. A class yields selectable methods when pytest would collect it under the default collection rules. That holds when the class name starts with Test, and it also holds when the class resolves to a unittest TestCase under the resolution FIX-9 states, which covers unittest style classes whose own name does not start with Test and indirect subclasses alike. A class that meets neither rule yields no selectable methods, and a method whose name does not start with test is never a selectable item in any class. The Round 2 review fixes below amend the naming half of this obligation, which in its first form claimed a pytest equivalence the name rule alone could not keep. This is covered by tests in tests/test_methods.py and tests/test_round2_fixes.py.

Obligation E3 covers the amended whole file fallback and amends FIX-3 where they conflict. A file that carries at least one selectable test item, whether a top level test function or a selectable test method, is judged by the rollup over its items and its whole file flag is false, even when every item in the file lives inside a class. The whole file judgement from FIX-3 remains only for a test file with no selectable test items at all, and the file level entry still records that the whole file path judged it when that path applies. A file is never silently skipped under either path. This is covered by tests in tests/test_methods.py and tests/test_round1_fixes.py.

Obligation E4 covers the rollup over methods. The file level verdict treats a method exactly like a top level function. One class holding a strong method and a decorative method reports the two methods with different verdicts, and the file rolls up under the rule in D2 as amended by FIX-2. A baseline failure in a method blocks a decorative headline for its file exactly as a baseline failure in a function does, and a judged method that can fail makes its file able to fail however many decorative siblings it has. This is covered by tests in tests/test_methods.py.

Obligation E5 covers the report format version for this slice. The JSON report carries a top level field named schema and its value is cantfail-report/3. The version moves because the functions list of a file verdict now carries method entries beside function entries, and a reader of format 2 data must never mistake a method entry for a top level function that happens to share its bare name. The text report prints the same schema value on its schema line and shows a method entry on the same kind of line it uses for a function entry, under the name the method carries in the file verdict. This is covered by tests in tests/test_report.py and tests/test_cli.py and tests/test_methods.py.

Obligation E6 covers duplicate method names. A method name defined twice inside one class is judged once, under the single node pytest can run, and the earlier definition is never reported as judged on its own. The same method name defined in two different classes names two different nodes and is judged once in each class. A test function name defined twice at module level keeps the behaviour FIX-1 already states. This is covered by tests in tests/test_methods.py and tests/test_round1_fixes.py.

Obligation E7 covers the limits of selection, stated so they are decisions and not discoveries. Selection follows the default pytest collection rules as E2 states them and cantfail does not read collection settings from the analysed project. A project that changes its test class prefix or its test function prefix in its own pytest settings can hold items this selector does not name, and any file whose items are all of that kind falls to the whole file fallback while a file mixing both kinds is judged on the items the selector names. Classes nested inside other classes are not selected, and a file whose tests live only in a nested class is judged by the whole file fallback. When a file mixes named items with test shaped definitions the selector does not name, the file verdict says so under FIX-12 rather than presenting its headline as a verdict on every test shaped definition in the file. The slice 4 obligations below amend the first sentence of this obligation where they conflict, because the selector now reads the collection naming settings of the analysed project under F1 to F4. This is covered by tests in tests/test_methods.py and tests/test_round2_fixes.py.

## Round 2 review fixes

The Round 2 two axis review and red team found that the selector, which is a syntactic reading of the source, diverged from what pytest actually collects in both directions, and that the file headline could speak for tests that were never judged. The obligations below amend E1 and E2 and E7 where they conflict, and each one is covered by tests in tests/test_round2_fixes.py unless it says otherwise.

Obligation FIX-8 covers inherited methods. A test method inherited from a local base class is judged under the class pytest collects it on, named with that class and the method joined the way a pytest node joins them. A file whose only strong test is an inherited method therefore reports that the test can fail, and no mutant the inherited method kills is ever listed as one that walked through.

Obligation FIX-9 covers TestCase resolution. A class counts as a TestCase class when it resolves to the unittest TestCase through names the module itself binds, a direct import of TestCase under any local name, the TestCase attribute of an imported unittest module, or a local class that itself resolves to a TestCase. A base whose name merely ends in TestCase and resolves to nothing in the module does not count, so a namesake class can no longer manufacture items pytest never collects. Indirect subclasses through local intermediate classes are selected, which closes the miss direction of the first form of E2.

Obligation FIX-10 covers classes pytest refuses. A plain class that defines an init of its own yields no selectable methods, because pytest collects nothing from it, while a TestCase subclass keeps its methods under unittest semantics even with an init of its own. A class that sets __test__ to False yields no selectable methods whatever its name or bases. No item the selector names may be one pytest cannot collect, so no method is ever labelled a baseline failure for the reason that it does not exist.

Obligation FIX-11 covers duplicate class names. A class name defined twice binds its last definition exactly as the module does, and only that definition yields items, so a shadowed class contributes no phantom method beside the real one.

Obligation FIX-12 covers partial selection disclosure. When a file holds test shaped definitions the selector does not name beside at least one named item, the file verdict carries a partial selection flag in the JSON report and a line in the text report saying the verdict covers the named items only. The same change adds the whole file and no tests flags to every file entry in the JSON report, which is additive inside format 3.

Obligation FIX-13 covers the nothing collected label. A whole file run in which pytest collected nothing at all is a file with no tests in it, not a failing suite. Its verdict reads no applicable mutants and the report carries a no tests flag and a line saying so, instead of the baseline failure label the first form of this slice gave it.

## Slice 4 obligations

The slice 4 obligations below amend E7 where they conflict, and the conflict is named in each one. E7 stated that cantfail does not read collection settings from the analysed project, so a project that renames its test functions or classes or files in its own pytest settings holds items the selector does not name. Slice 4 retires that limit for the three naming settings and for the sources named in F1, and E7 keeps its force for everything beyond that reach. Each obligation is covered by tests in tests/test_slice4.py unless it says otherwise.

Obligation F1 covers reading the settings. Cantfail reads the collection naming settings of the analysed project from the project root alone and from one source alone. The source is the first of these that pytest would treat as its config file for the project, in this order. A pytest.ini file in the root wins first, and its settings live in the section named pytest. The pytest ini options table of a pyproject.toml file in the root wins next, and that file counts as a source only when it carries that table. A setup.cfg file in the root wins next, and its settings live in the section named tool:pytest. A tox.ini file in the root wins last, and its settings live in the section named pytest. The settings read are python_functions and python_classes and python_files, and no other setting is read. A source that cannot be parsed contributes no settings and no later source is read in its place, so a broken file yields the defaults rather than a guess drawn from a file pytest would never reach. A project with no such source is read with the defaults in force, exactly as before this slice.

Obligation F2 covers what a setting value means. Each setting is a list of patterns in the pytest sense. A function name or a class name matches a pattern when the name starts with the pattern or matches the pattern as a glob, which is the matching pytest itself applies to those two settings. A file name matches a python_files pattern when the pattern matches the file name alone as a glob, with the path never taking part. An absent setting means the default for that setting is in force and an empty list in a settings source means what pytest would make of it, which is that no name matches on that setting.

Obligation F3 covers the selector honouring the function and class settings and amends E2 where they conflict. A function name or a method name is a selectable item name when it matches any pattern of the python_functions setting in force, or when no such setting is in force and the name starts with test. A class yields selectable methods when it resolves to a unittest TestCase under FIX-9, or when its name starts with Test, or when its name matches any pattern of the python_classes setting in force, and the name based rules stay subject to the FIX-10 refusals, so a class that sets __test__ to False yields nothing and a name based class that defines an init of its own yields nothing, while a TestCase class keeps its methods under unittest semantics. A name a custom pattern selects is judged exactly like a default name, under the same five verdict values and the same rollup, and no other selection rule changes in this slice.

Obligation F4 covers discovery honouring the file setting and amends E7 where they conflict. A python file in the project is a test file when its name matches any pattern of the python_files setting in force, or when no such setting is in force and its name starts with test_ or ends with _test.py, which are the shapes discovery has always used. Pairing keeps the rule C8 states, so a file discovered only through a custom pattern pairs with every non test source module in the project when no module shares its stem, and a custom file name is never stripped to invent a pairing.

Obligation F5 covers report disclosure and the report format decision. When at least one naming setting in force differs from its default, the JSON report carries a top level entry named collection_settings and the entry names each non default setting with the patterns in force for it, and the text report names the same settings and patterns on one line. When every setting is at its default the entry and the line are both absent, and their absence means defaults were in force. The schema stays at cantfail-report/3 and does not move for this slice. The reasoning is that the entry is additive context about why items were named and it changes no verdict and no existing field, so a reader of format 3 loses nothing about any verdict by ignoring it, which is the same ground on which FIX-12 added fields inside format 3. A deliberate consequence is that a project with no settings source regenerates reports byte identical to the reports of the earlier slices.

Obligation F6 covers honest limits that stay after this slice, stated so they are decisions and not discoveries. Settings that live anywhere other than the four sources of F1 are not read, and settings carried on a pytest command line are not read, and collection behaviour beyond naming, such as test paths or directory patterns or marker rules, is not modelled. The analysed project is still judged by running pytest in the scratch copy under the very settings the selector read, so where the selector and pytest diverge the run decides the baseline and the report shows the outcome rather than hiding it. A project whose items are named only through its settings, analysed with the settings source removed, behaves exactly as E7 described before this slice, falling to the whole file fallback and carrying the no tests flag under FIX-13 when pytest collects nothing there.

## Round 3 review fixes

The Round 3 red team compared this slice against the pytest installed on this machine and found five places where the tool stated things that pytest contradicts, and the two axis review added the crash a wrong shaped settings file could cause. The obligations below amend F1, F2, F3, F5 and F6 where they conflict, and each one is covered by tests in tests/test_round3_fixes.py unless it says otherwise. Two tests in tests/test_slice4.py that had enshrined the earlier readings were corrected in the same pass and are named in the obligations they belong to.

Obligation FIX-14 covers the source set and its order. The sources are the files pytest itself searches, in the order pytest searches them, which is pytest.toml ahead of .pytest.toml ahead of pytest.ini ahead of .pytest.ini ahead of pyproject.toml ahead of tox.ini ahead of setup.cfg. A pytest.toml file is always a source and holds its settings in a pytest table in native form. A pyproject.toml counts through its pytest table holding the settings directly in native form or under an ini options table in string form, and a file holding both forms at once is a broken source because pytest refuses it. A settings table of the wrong shape is a broken source as well. The broken source rule of F1 covers every one of these shapes, so each contributes nothing and blocks the sources behind it. This obligation amends the source list and order F1 first stated.

Obligation FIX-15 covers the class name rule. A python_classes setting in force replaces the Test prefix entirely, the way a python_functions setting replaces the test prefix, so the selector never names a class the project's own settings have deselected and no method is ever labelled a baseline failure for the reason that its class does not exist under those settings. The TestCase resolution of FIX-9 is untouched, and a TestCase class yields its methods under any setting. This obligation amends the class sentence of F3, and the slice 4 test that pinned the earlier beside the defaults reading is corrected to pin replacement.

Obligation FIX-16 covers path carrying file patterns. A python_files pattern holding a path separator matches against the project relative path of a file as a glob, and a pattern holding no separator matches the file name alone, which is the rule pytest itself applies. A test file under a sub folder named by a path carrying pattern is therefore discovered rather than silently vanishing from the analysis. This obligation amends the matching sentence of F2 and the discovery rule of F4.

Obligation FIX-17 covers setting value shapes. A scalar value in a settings table reads as its string form, the conversion pytest applies to scalar values of its own, and no value shape a settings file can hold crashes the analysis. A malformed analysed project yields a report read under the defaults the broken source rule gives, never a traceback in the auditor.

Obligation FIX-18 covers what the disclosure calls a difference. The entry and the line of F5 name only the settings whose patterns differ from the pytest defaults for that setting. A project that restates a default value exactly has nothing non default in force and discloses nothing, so the absence of the entry and the presence of the entry are both truthful. This obligation amends the difference sentence of F5.

Obligation FIX-19 covers the shaped name reading behind the partial selection flag. A definition name counts as a test shape under the python_functions setting in force when one is set, its patterns replacing the test prefix entirely, and under the test prefix when none is set. A name the project's own settings have deselected therefore never reads as an unjudged test shape, and a file the project gate judges in full is not flagged as partly judged. This obligation amends the shaping rule FIX-12 stated.

Three limits are stated here so they are decisions and not discoveries, amending the claim F6 first made. The settings are read at the project root alone, and pytest locates its config upward from the nodes it is asked to run, so a config file below the project root can govern a run the selector read under the root settings, and where the two diverge the run still decides the baseline under its own config. A setup.cfg carrying a plain pytest section makes the project's own pytest fail outright with an unsupported section error, and cantfail does not model config hard failures of that kind. The static scan of the earlier slices keeps its own test prefix rule and does not follow the naming settings, which is a scope statement about the scan and not a claim about collection.

## Slice 5 obligations

The slice 5 obligations below amend the scan scope statement of the Round 3 review fixes where they conflict, and the conflict is named in G2. That statement said the static scan keeps its own test prefix rule and does not follow the naming settings, so a function the selector names through a custom pattern could sit outside the reading the scan applied and a function the project settings deselect could still be flagged. Slice 5 retires that limit for the function naming setting. Each obligation is covered by tests in tests/test_slice5.py unless it says otherwise.

Obligation G1 covers the scan taking the settings. The static scan reads one test file under the collection naming settings of the analysed project. The scan entry points take the settings the way the selector takes them, with the defaults in force when none are given, and the runner passes to every scan it makes of a project file the very settings it loaded for that project under F1. No second reading of any settings source happens for the scan, and a scan made outside an analysed project runs under the defaults exactly as before this slice.

Obligation G2 covers what counts as a test function for the scan and amends the scan scope statement of the Round 3 review fixes where they conflict. A static finding is reported only for an assertion that sits inside a test function. A function definition is a test function for the scan when its name matches any pattern of the python_functions setting in force, or when no such setting is in force and its name starts with test, which is the replacement reading the selector applies to that setting under F3. An assertion belongs to the outermost function definition on the climb from the assertion to the module that sits at module level or directly inside a module level class, and that definition alone decides, so an assertion inside a definition nested in a test function belongs to the test function and an assertion inside a test named definition nested in a helper belongs to the helper. An assertion at module level sits inside no function and earns no finding. The rule reaches every pattern the scan applies, the direct and indirect mock forms of C1 and the helper and fixture form of D5 and the self comparison and constant true forms, because each of them is a claim about a test assertion. The maps the scan builds while reading a file, the configured return values of C1 and the helper and fixture tables of D5, stay file wide as the earlier slices built them, because a helper is not a test function and is never required to be one for the test that binds its mock to be flagged.

Obligation G3 covers the class question, stated rather than ruled. No pattern the scan applies keys on a class name, so the scan takes no class name rule of its own in this slice and the python_classes setting does not reach the scan. A method is a function definition for the rule of G2 and its own name decides whether the assertions inside it earn findings, whatever the enclosing class is called and whether or not the selector would collect that class. This is a stated limit of the slice and not an oversight, and it matches the name only reading the shaped name rule of FIX-19 already gives methods outside the selector.

Obligation G4 covers the boundary with the verdict path. This slice changes which definitions earn static findings and nothing else. Item selection and discovery and every verdict follow F3 and F4 and the earlier obligations exactly as before, and the settings reach the scan only along the path G1 states. A project whose settings deselect a test prefixed mock shaped function reports neither a verdict item nor a static finding for that function, so the report never points a finding at a function the same report treats as not a test.

Obligation G5 covers the report format decision. The schema stays at cantfail-report/3 and does not move for this slice. A static finding gains no new field and no existing field changes meaning, and the change is only in which definitions earn findings, driven by settings the report already discloses under F5 whenever they differ from the defaults. A reader of format 3 loses nothing about any verdict or any finding by ignoring the change, which is the same ground on which F5 kept the schema for slice 4. A deliberate consequence is that a project with no settings source at non default values keeps the findings the earlier slices gave it on every shape that sits inside a test function.

Obligation G6 covers what changes at every settings value, stated so it is a decision and not a discovery. The earlier slices read a whole test file with one walk and reported a shape wherever it sat, so a shape inside a helper definition or at module level was reported beside the shapes inside tests. Under G2 such a shape sits inside no test function and earns no finding at any settings value, the defaults included, because a finding is a claim about a test and the scan now says which definitions are tests. Every finding the earlier slices reported on a shape inside a test function is still reported when the defaults are in force, the demo reports regenerate byte identical, and the earlier scan tests pass unaltered, which together are the evidence that the default reading of the scan is unchanged where tests are concerned.

## Round 4 review fixes

The Round 4 red team found one duplicated finding on the nested shape slice 5 claims, and one contract sentence the refused class report falsifies. The obligations below amend G2 and G4 where they conflict, and each one is covered by tests in tests/test_round4_fixes.py unless it says otherwise.

Obligation FIX-20 covers the helper and fixture findings inside nested definitions. Each function body is scanned exactly once for those findings. The scan enters at the definitions whose governing function is themselves, and its walk crosses into a nested definition with a copy of the enclosing bindings plus the nested definition's own fixture arguments, the way a closure reads the enclosing scope, and never enters the same body again from a second call. Before this fix the walk and the per definition calls overlapped, so an assertion whose binding and assertion both sat inside a definition nested in a test function was reported twice, as two identical findings on one line.
